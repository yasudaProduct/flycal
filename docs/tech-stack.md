# 技術選定ドキュメント

## 1. アプリ概要

本アプリは、ライブ・イベントのフライヤー画像からイベント情報を読み取り、カレンダーへ予定登録できるスマホアプリである。

主な利用シーンは以下。

- ライブ、イベント、展示、フェスなどのフライヤー画像を読み込む
- 画像内のイベント名、日付、時間、場所などを抽出する
- ユーザーが抽出結果を確認・修正する
- 端末のカレンダーアプリへ予定を登録する

MVPでは、画像から予定登録までの体験を最短で検証することを優先する。

## 2. 基本方針

### 2.1 MVPで重視すること

- 画像から予定情報を正しく抽出できること
- 予定登録までの操作が少ないこと
- ユーザー登録なしで試せること
- LLM利用料を制御できること
- iOS / Android の両方を視野に入れること

### 2.2 MVPで重視しないこと

- 複数端末同期
- 解析履歴のクラウド保存
- Google Calendar APIによる直接同期
- ユーザーアカウント管理
- 高度な課金管理

## 3. 決定事項

### 3.1 スマホアプリ

**採用技術**

- React Native
- Expo

**採用理由**

- iOS / Android を同一コードベースで開発できる
- TypeScriptベースで開発できる
- MVP開発速度を優先できる
- Expoでカメラ、画像選択、権限管理、カレンダー連携が扱える
- SwiftUIを使わなくてもMVP要件を満たせる見込みがある

**iOS実機検証**

- Apple Developer Programを利用する前提とする
- TestFlightは外部テストや配布検証時に利用を検討する

**補足**

SwiftUIは現時点では採用しない。iOS固有機能を高度に使う必要が出た場合に再検討する。

### 3.2 カレンダー連携

**MVPでの採用方針**

- 端末標準カレンダー連携
- Expo Calendarを利用する想定

**ユーザー体験**

1. ユーザーが画像を選択する
2. 画像からイベント情報を抽出する
3. ユーザーが抽出結果を確認・修正する
4. 「カレンダーに追加」を押す
5. 初回のみカレンダー権限を許可する
6. 端末標準カレンダーへ予定を登録する

**採用理由**

- Googleログインが不要
- OAuth実装が不要
- Apple Calendar / Google Calendar / Outlookなど、端末に設定されているカレンダーへ登録できる
- MVPとして十分シームレスな体験を提供できる

**Google Calendar APIについて**

MVPでは採用しない。
将来的には、Google Calendarへ直接登録したいユーザー向けに追加する可能性がある。
その場合でも、アプリ独自のユーザー登録は必須ではなく、Google OAuth認証で連携可能。

### 3.3 Web / LP

**採用方針**

- Cloudflare上で構築する
- LPを作成する
- 将来的にWeb上でもお試し機能を提供する可能性がある

**想定機能**

- サービス紹介
- 画像アップロードによるお試し解析
- 解析結果の表示
- .icsファイル生成
- Google Calendar追加リンク

**補足**

Web版では端末カレンダーAPIのようなシームレスな登録は難しいため、.icsファイル生成やGoogle Calendar追加リンクを主な候補とする。

### 3.4 バックエンド

**採用技術**

- Hono
- Cloudflare Workers

**採用理由**

- Cloudflare Workersと相性が良い
- 軽量でMVP向き
- TypeScriptでアプリ・Webと技術スタックを揃えやすい
- API実装がシンプル

**バックエンドの主な役割**

- 画像アップロード受付
- LLM API呼び出し
- LLM APIキーの秘匿
- 画像からのイベント情報抽出
- 構造化JSONの返却
- 月間利用回数の管理
- 利用ログ、エラーログの保存
- 将来的な課金状態管理

### 3.5 DB

**採用技術**

- Cloudflare D1

**採用理由**

- Cloudflare上で完結しやすい
- MVPで扱うデータ量が少ない
- 匿名ユーザーID、利用回数、ログ管理には十分
- 低コストで開始できる
- Cloudflare Workersとの統合が容易

**注意点**

D1はPostgreSQLではなく、SQLite系のサーバーレスDBである。
MVPでは問題ない想定だが、将来的に複雑な検索、集計、大量データ処理が必要になった場合は、Neon PostgreSQLなどへの移行を再検討する。

### 3.6 ストレージ

**現時点の方針**

- 画像は原則保存しない

**理由**

- 個人情報・プライバシーリスクを下げる
- ストレージコストを抑える
- MVPの実装を簡略化する

**将来的な候補**

画像保存が必要になった場合は、Cloudflare R2を候補とする。

### 3.7 認証

**MVPでの方針**

- ユーザー登録なし
- 匿名ユーザーIDで管理する

**匿名ユーザーIDの用途**

- 月間利用回数の管理
- 不正利用の簡易抑止
- 将来的な課金状態との紐付け
- 利用ログ分析

**補足**

匿名IDはアプリ初回起動時に生成し、端末内に保存する想定。
ただし、以下の制約がある。

- アプリ削除で識別できなくなる可能性がある
- 端末変更時に引き継げない
- 複数端末では別ユーザー扱いになる
- 厳密な不正利用対策にはならない

MVPでは許容する。

### 3.8 課金体系

**現時点の有力方針**

- 広告
- 月○回まで無料

**想定例**

- 無料ユーザー：月5回まで解析可能
- 広告表示あり
- 将来的にプレミアムプランを追加する可能性あり

**将来的な課金候補**

- 月額サブスク
- 広告非表示
- 解析回数無制限
- 追加チケット購入

**補足**

Apple App Store / Google Play にはサブスク課金の仕組みがあるため、将来的な有料プランではストア課金を利用する方針が現実的。

### 3.9 LLM利用

**採用方針**

- Geminiを利用する
- リリース時点ではVertex AI経由で利用する方針
- APIキーはクライアントに持たせない
- バックエンド経由でLLMを呼び出す
- 抽出結果は構造化JSONで返却する

**開発時の補足**

MVP開発中は、必要に応じてGemini Developer APIを利用して検証する可能性がある。

**抽出対象の例**

- イベント名
- 開催日
- 開始時間
- 終了時間
- 会場名
- 住所
- 出演者
- 説明文
- 公式URL
- 信頼度
- 不明項目

**補足**

フライヤーは文字装飾、複数日程、縦書き、手書き風フォントなどがあるため、抽出後にユーザー確認画面を必ず設ける。

## 4. 現時点の全体構成

```text
[React Native + Expo]
  ├─ 画像選択 / カメラ
  ├─ 解析結果確認UI
  └─ 端末カレンダー登録

[LP / Web]
  ├─ Cloudflare上で公開
  └─ 将来的にWebお試し機能

[Backend]
  ├─ Hono
  ├─ Cloudflare Workers
  ├─ LLM API呼び出し
  ├─ 利用回数制限
  └─ ログ管理

[DB]
  └─ Cloudflare D1

[Storage]
  └─ 原則なし
     必要時のみCloudflare R2
```

## 5. MVPの想定ユーザーフロー

```text
アプリ起動
↓
画像を選択
↓
バックエンドへ画像送信
↓
LLMでイベント情報を抽出
↓
抽出結果を確認・修正
↓
カレンダーに追加
↓
端末標準カレンダーへ予定登録
```

## 6. MVPで必要な主なテーブル案

### users

匿名ユーザーを管理する。

| カラム | 内容 |
| --- | --- |
| id | 内部ユーザーID |
| anonymous_id | 端末側で生成した匿名ID |
| created_at | 作成日時 |
| last_seen_at | 最終利用日時 |

### usage_monthly

月間利用回数を管理する。

| カラム | 内容 |
| --- | --- |
| id | ID |
| user_id | users.id |
| year_month | 対象月 |
| analysis_count | 解析回数 |
| created_at | 作成日時 |
| updated_at | 更新日時 |

### analysis_logs

解析ログを管理する。

| カラム | 内容 |
| --- | --- |
| id | ID |
| user_id | users.id |
| status | success / failed |
| extracted_event_date | 抽出されたイベント日 |
| llm_model | 使用モデル |
| token_usage | トークン使用量 |
| error_message | エラー内容 |
| created_at | 作成日時 |

画像そのものは保存しない方針。

## 7. 現時点の補足事項

### 7.1 Google Calendar APIについて

MVPでは採用しない。
将来的には、Google Calendarへ直接登録したいユーザー向けに追加する可能性がある。
その場合でも、アプリ独自のユーザー登録は必須ではなく、Google OAuth認証で連携可能。

### 7.2 DBについて

Cloudflare D1はSQLite系DBである。
MVPでは十分と判断しているが、将来的に複雑な分析、大量データ処理、検索要件が強くなった場合は、PostgreSQL系DBへの移行を再検討する。

### 7.3 認証について

MVPではユーザー登録は行わず、匿名ユーザーIDで利用回数を管理する。
将来的に以下が必要になった場合は、ユーザー登録を再検討する。

- 他端末同期
- バックアップ
- 履歴同期
- Web版との連携
- 課金状態同期
